SYSTEM · CASE STUDY

Replan

灵活规划 · 长期任务的拆解 · 排期 · 自适应重排系统。
对话式规划引擎：一句话说个目标 → 拆成可执行子任务 → 按 deadline / 作息智能排期 → 反馈后自动重排。LLM 负责理解语义，确定性引擎负责排得对。

类型 · 对话式规划系统 角色 · 独立开发 ~265 项自动化测试 · CI

一句话

一个面向学生 / 个人效率场景的对话式规划系统。用户用自然语言输入「帮我七天学完一个课程」或「今天只完成了一半」，系统自动拆解任务、安排时间、展示周视图，并在反馈后重新规划剩余日程。

为什么做（问题）

普通日历只能存「事件」，不理解「任务」。真实痛点不是「记个时间」，而是：有个目标（写论文 / 学课程），却不知道怎么拆、每天做什么、做不完怎么调整。

所以目标不是「做个日历」，而是做一个能理解任务、安排时间、并在进度变化后自动重排的系统。

定位

不是聊天机器人 是围绕「任务状态」运转的规划系统——每次输入都改变当前计划，而非只回一段话。
任务-时间双向闭环 任务理解 → 时间安排 → 状态更新 → 自动重排，连成完整回路。

架构 · 语义层 vs 正确性层

整个项目最关键的一条分界：让 LLM 只做它擅长的语义理解，把排期的正确性交给确定性引擎。

成长主线 · 一次「从选框架到分层」的转变

01

第一幕 · 拆成多引擎（规则 + LLM 混合）

最初把能力拆成独立引擎：T02 拆解 / T03 排程 / T04 反馈解析 / T05 重排 + Orchestrator 路由。优点是职责清楚、易单测、易定位。

代价开始显现：跨模块数据结构必须严格一致，中间任一层格式偏一点，用户看到的就是「整个计划都不对」，但根因藏在任意一层的缝隙里。

02

第二幕 · 怀疑架构，做 A/B 实验

复杂度上来后我开始问：「是不是直接全交给 AI 更简单？」我没停在想法，而是真做了两条实验链路（langgraph-practice 分支）：LangGraph 编排 / 单次 LLM JSON。

结论很关键——三条路单独都不行：

  • 纯规则：稳，但死板，不懂自然语言的灵活诉求。
  • 全 LLM / 单次 JSON：灵活，但不稳——拆解抽象、排期会重叠 / 把任务丢掉、结果不可控。
  • LangGraph：让编排更清晰，但没解决真正的问题（问题不在编排形式）。
03

第三幕 · 转变——不是「选一个框架」，而是「分层 + 评测驱动」

真正的顿悟是：卡点根本不在「用规则还是 LLM 还是 graph」，而在 ① 领域建模和确定性排程算法本身；② 没有可信的评测。于是两个决定：

  • 分层：让 LLM 只做语义理解，把排期正确性交给确定性引擎（不会排出重叠 / 丢任务 / 塌缩）。意图进一步收敛成 6 个纯语义意图 + 状态机解析，不再让 LLM 和规则互相打架。
  • 评测驱动：我发现原本「全绿」的评测报告其实是伪造的、和真实链路脱节。于是重建了端到端确定性评测 + LLM-as-judge 质量评测 + 覆盖矩阵 + CI，把「感觉对了」变成「数据证明对了」，再据此系统性修复。

这一幕是整个项目最有价值的部分：我从「加功能 / 修 bug」进入到「系统设计 + 评测文化」。

具体难点 & 怎么解

难点现象解决
拆解「像对了」但抽象LLM 输出「学习监督学习基础」这类占位 / 大块few-shot + 抽象↔具体对照 + 调用重试；拆解质量 66→85（LLM-as-judge）
排期堆在同一天贪心塞满，「7 天计划」3 天排完从「正向贪心」改为按 deadline 反推均摊；排不下溢出而非丢弃
新旧任务重叠每个入口各写避让 → 失控时间槽后处理统一收口：共享 find_available_slot + validate_no_overlap
模糊反馈难「做了一半」要定位任务、算剩余、重排统一 task_id / slot 结构，反馈与重排复用同一套时间表管线；补范围序数 / 取消 / 模糊澄清
隐藏 bug建评测时暴露 8 个此前看不见的真 bug时长塌缩成 1h、分数小时假重叠崩溃、意图误判等，逐个修

结果

66 → 85拆解质量（LLM-as-judge）
83% → 100%意图准确率（收敛后）
~265项自动化测试（后端 249 + 前端 16）
12/12端到端评测通过 · T04→T05 8/8
0重叠 / 碎片 / 丢任务 / 塌缩
CIGitHub Actions 守护（pytest + 端到端 + 前端）

新增能力：时间约束（「周三上午有课别排」）、个人作息画像 + 预设身份、改排已有计划、从反馈学各类任务的估时倍率。

我的思考（成长 / 反思）

这个项目最有价值的不是把页面做出来，而是让我从「功能开发」进入「系统设计」：

  • 任务状态该用什么结构贯穿全链路？
  • 规则编排什么时候会失控？纯 LLM 什么时候更划算？成本边界在哪？
  • 怎么判断「它真的对了」——而不是「看起来对了」？

我没停在「怀疑架构」，而是真做了 LangGraph 和单次 LLM 两种实验去比较稳定性 / 灵活性 / 维护成本；最后想明白答案不是二选一，而是分层 + 用评测把正确性钉死。这让项目从一个产品原型，变成了一个「AI 应用编排方式」的实验场。

当前状态与下一步

✅ 已完成：核心闭环（拆解→排期→反馈→重排）、时间约束 / 作息画像、改排、个性化估时、今日视图、评测体系 + CI。

⏳ 优化中 / 未做：图片 / 文件输入（多模态）、复杂反馈的语义匹配更稳、单次 LLM 链路的拆解约束更强、活动提取 / 消费记录等 P1 模块。
