SYSTEM · CASE STUDY

灵活规划（Replan）

反馈驱动的持续规划系统 · 传统日程工具的问题不是记录，而是计划生成之后，世界就变了。
尝试把「一次生成计划」改成「持续规划」：LLM 负责理解与拆解自然语言任务，规则引擎负责排期与重排。各模块已经分别实现，但真实端到端交互仍在收束中。

状态 · V1 原型归档 / V2 进行中 角色 · 独立开发 阶段 · 模块实现与场景联调

Demo

展示输入一个大任务、生成七天计划，并在周视图中反馈任务进度的当前原型。

一句话

一个面向学生 / 个人效率场景的对话式规划原型。系统已分别实现自然语言任务拆解、排期、周视图与反馈重排模块；目前仍在联调这些模块在同一真实交互中的状态传递和冲突处理。

为什么做（问题）

普通日历只能存「事件」，不理解「任务」。真实痛点不是「记个时间」，而是：有个目标（写论文 / 学课程），却不知道怎么拆、每天做什么、做不完怎么调整。

所以目标不是「做个日历」，而是做一个能理解任务、安排时间、并在进度变化后自动重排的系统。

定位

不是聊天机器人 目标是围绕「任务状态」运转：计划相关输入应改变当前计划，而非只返回一段文字。
目标闭环：任务-时间双向更新 目标路径是任务理解 → 时间安排 → 状态更新 → 自动重排；当前仍在解决跨模块状态同步与冲突处理。

架构 · 语义层 vs 正确性层

整个项目最关键的一条分界：让 LLM 只做它擅长的语义理解，把排期的正确性交给确定性引擎。

成长主线 · 一次「从选框架到分层」的转变

01

第一幕 · 拆成多引擎（规则 + LLM 混合）

最初把能力拆成独立引擎：T02 拆解 / T03 排程 / T04 反馈解析 / T05 重排 + Orchestrator 路由。优点是职责清楚、易单测、易定位。

代价开始显现：跨模块数据结构必须严格一致，中间任一层格式偏一点，用户看到的就是「整个计划都不对」，但根因藏在任意一层的缝隙里。

02

第二幕 · 怀疑架构，做 A/B 实验

复杂度上来后我开始问：「是不是直接全交给 AI 更简单？」我没停在想法，而是真做了两条实验链路（langgraph-practice 分支）：LangGraph 编排 / 单次 LLM JSON。

结论很关键——三条路单独都不行：

  • 纯规则：稳，但死板，不懂自然语言的灵活诉求。
  • 全 LLM / 单次 JSON：灵活，但不稳——拆解抽象、排期会重叠 / 把任务丢掉、结果不可控。
  • LangGraph：让编排更清晰，但没解决真正的问题（问题不在编排形式）。
03

第三幕 · 转变——不是「选一个框架」，而是「分层 + 评测驱动」

真正的顿悟是：卡点根本不在「用规则还是 LLM 还是 graph」，而在 ① 领域建模和确定性排程算法本身；② 没有可信的评测。于是两个决定：

  • 分层：让 LLM 只做语义理解，把排期、冲突检测与状态更新交给确定性模块。这个设计降低了单点不确定性，但跨模块数据契约仍需要继续收束。
  • 评测驱动：我发现原本「全绿」的评测与真实链路脱节，于是开始重建端到端场景、质量评测与覆盖矩阵。当前评测能暴露问题，但尚未形成稳定的端到端验收基线。

这一幕是整个项目最有价值的部分：我从「加功能 / 修 bug」进入到「系统设计 + 评测文化」。

具体难点 & 怎么解

难点现象解决
拆解「像对了」但抽象LLM 输出「学习监督学习基础」这类占位 / 大块加入 few-shot、抽象↔具体对照与调用重试，并继续用真实任务校准拆解粒度
排期堆在同一天贪心塞满，「7 天计划」3 天排完从「正向贪心」改为按 deadline 反推均摊；排不下溢出而非丢弃
新旧任务重叠每个入口各写避让 → 失控时间槽后处理统一收口：共享 find_available_slot + validate_no_overlap
模糊反馈难「做了一半」要定位任务、算剩余、重排统一 task_id / slot 结构，反馈与重排复用同一套时间表管线；补范围序数 / 取消 / 模糊澄清
跨模块隐藏问题单个模块测试通过，接到真实交互后仍出现异常针对时长塌缩、分数小时冲突、意图误判与状态不同步逐项定位

项目结果

该项目尚未形成稳定上线版本，但通过实际开发暴露了 Agent 系统中「局部模块通过不等于端到端可用」的问题，也促使我重新设计评测、验收与变更管理流程。

我的思考（成长 / 反思）

这个项目最有价值的不是把页面做出来，而是让我从「功能开发」进入「系统设计」：

  • 任务状态该用什么结构贯穿全链路？
  • 规则编排什么时候会失控？纯 LLM 什么时候更划算？成本边界在哪？
  • 怎么判断「它真的对了」——而不是「看起来对了」？

我没停在「怀疑架构」，而是真做了 LangGraph 和单次 LLM 两种实验去比较稳定性 / 灵活性 / 维护成本；最后想明白答案不是二选一，而是分层，并用评测持续暴露端到端问题。这让项目从一个产品原型，变成了一个「AI 应用编排方式」的实验场。

当前状态与下一步

当前状态：V1 已完成核心模块与部分场景测试，但端到端仍存在状态不同步、任务冲突与反馈后重排偏差，作为原型归档；V2 正在统一状态契约、重建验收基线并收束最小稳定闭环。

下一步：先统一跨模块状态结构和验收场景，解决任务冲突与反馈重排偏差；在最小闭环稳定之前，不继续扩展多模态输入和其他 P1 功能。

技术栈

React / Vite 前端 · Python HTTP API 后端 · LLM + 本地规则兜底 · 确定性排期与重排模块 · 单元测试 / 场景评测脚本。
